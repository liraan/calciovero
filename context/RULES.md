# Rules — how we work on Calcio Vero

**What this is.** The working rules agreed with the maintainer, for any AI (or person) that works on the repository. It replaces `NEW-SESSION-PROMPT.md`, `AGENT-POLICY.md`, `NOTA-PER-NUOVA-AI.md`, `GITHUB-SESSION-PROMPT.md` and `DECISION-PATTERNS.md` (2026-11-13; the old texts are in `git log`). Only the rules still in use are here. Hard stops are marked 🛑: D1, D2, C2. In a conflict the hard stops win, D1 first; otherwise ask the maintainer.

**To start a session, paste this:** *"Read `context/RULES.md` and `context/STATE.md`, run `bash context/scripts/session.sh start`, report, then wait."*

## A. The pact and the filters

- **A0 — The pact.** The maintainer: *"the project is ours, not mine; on the code you are the expert"*. On the code the agent decides and declares; on the model (what football is) and on priorities the maintainer decides. *"You can contradict me"*: contradiction is expected when the filters point there. When corrected, reformulate; do not defend.
- **A1 — Discuss before applying.** When the maintainer asks a question or proposes an idea, the answer is a discussion and a conclusion, not a change (*"era da discutere, non da applicare perché sì"*). Apply after he agrees. When a source already decides (VISION, an accepted ADR, the plan), derive, apply, declare: do not stop to ask.
- **A2 — Pausa, riprendi, chiudi.** "pausa" (from either side) suspends execution and opens a discussion. Only "riprendi" (resume) and "chiudi" (close, starts the closing ritual) exit it, written exactly. On "riprendi", the first act is to record what the pause produced (E3).
- **A3 — LUNA (the moon, not the finger).** Every reply starts with a `LUNA:` line: the property the example or the request reveals, in 1-3 sentences, without code identifiers. Widen the horizon; never read an example literally. Technical consequences go after, and only as far as asked.
- **A4 — Partita vera (the real match).** Every design decision of the engine answers three questions: *in a real match, how do the actors recognise this? what does it depend on? who produces it?* The answer goes in the commit message or the ADR. A decision without it is an opinion.
- **A5 — The direction, binding.** Every choice on the pitch is the player's own (ADR-049); no die in a simulation path (ADR-035); every act derives from its actor's characteristics and is recognisable, by twin test (ADR-051); the whole repertoire is in every match, in potential; every player thinks with his own mind, no weights per kind of option (ADR-052); the referee is the Laws applied objectively, present without occlusion. Use the words of modern football (`doctrine/GLOSSARY.md` §0: occupation of space, lines, half-spaces, not "position"). Finish L0 before L1.
- **A5-bis — Statistics are derived, never adjusted** (ADR-052 note, 2026-11-13). A number in `balance/` has a source, is computed from other numbers, or is declared arbitrary and left alone; it is never chosen by looking at the statistic it produces. A statistic far from the real one is a cause to find in how the players perceive, think or move.
- **A6 — Method for a task.** (1) a plan with the skeleton of the task; (2) step by step, each step checked through A3 and A4; (3) at the end, test, then fine calibration with the maintainer; (4) task done, next task. Statistics are measured during the work and compared at the end, never chased (A5-bis).
- **A7 — A conclusion, not a menu.** When the filters yield a default and the alternative can be tracked as an open item, apply the default and say so. Present options only when the choice is the maintainer's (model, priority).

## B. Honesty and doctrine

- 🛑 **D1 — Honesty.** If you have not read a file, say so. Never invent numbers, hashes, file contents or tool output. "I don't know" beats an invention. A trailer must be true, not only present: `Verified: C2-green` only if the full gate ran and passed in this session.
- 🛑 **D2 — Doctrine in the code.** No `unwrap`/`expect`/`panic!`, no `HashMap`, no platform imports (`gates.sh` B9) in simulation paths; no `unsafe`. The hidden plane (latents in `ds-db`) has no public fields, no `Serialize`, no getters. A change to the simulation model needs a `SIM_VERSION` bump, and an ADR when it changes a model form or an invariant. If a change contradicts `doctrine/00-foundations.md`, a doctrine ADR comes first.
- **D3 — Add only what is consumed today.** A structure enters with the code that uses it or the test that verifies it; a characteristic enters with its first consumer. Going against this is allowed when the cost is declared in the commit (`D3-check:`).
- **D4 — Refine before adding.** A working convention is made more mechanical, not replaced; a convention that does not work is replaced, not patched.
- **D5 — Mechanical where possible, visible otherwise.** A condition the maintainer cannot check without trusting the agent is a leak; where judgment is unavoidable, leave an artefact (a trailer, a line in the report, a test).
- **P — Patterns paid for.** A test that cannot fail is worse than none (check the sample is not empty). `grep` before saying "X reads this field". "Decided" is not "implemented": say which. After every edit, check that the edit happened (`grep -c` the new text, `git diff`), not only that the command exited.

## C. Git and quality

- **C1 — Commits.** Small, atomic, English, imperative mood. Push at a checkpoint or at the end, not after every commit. Two remotes: `origin` (GitHub, primary, CI) and `codeberg` (backup, Woodpecker): every push goes to both, `git push && git push codeberg main`; `git status -sb` must show no `[ahead]`. Phase 1: single maintainer, direct push to `main`; the GitHub ruleset (phase 2) returns with a second reviewer, a release, or an agent with a write token. An agent never force-pushes `main`, never merges, never tags without asking.
- 🛑 **C2 — Quality gate.** `cargo build --release`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`, `cargo fmt --check`, `cargo run --release --bin ds-test-runner -- --check --seed 42`, and `bash context/scripts/gates.sh`. All green or nothing is pushed. `bash context/scripts/session.sh close` runs them in order. Hooks (one-off: `git config core.hooksPath .githooks`): pre-commit (fmt, clippy, test on Rust changes), commit-msg (trailers, LCV), pre-push (clean tree, gates).
- **C3 — A behaviour change.** Bump `SIM_VERSION` in `ds-match/src/save.rs`; regenerate `EXPECTED` in `ds-match/tests/golden_l0.rs` (and its comment); add the entry to `L0-match/CHANGELOG-SIM.md`; a test that guards it (P1) and, for a new or changed act, a twin test; update the act's row in `L0-match/design/ACTIONS.md`. When the test count changes, update it in `README.md` (badge and text), `doctrine/STRUCTURE.md`, `CONTRIBUTING.md`, `doctrine/_index.md` (`gates.sh` A4 checks they agree with each other, not with reality).
- **C4 — Trailers.** Every commit that touches `context/STATE.md` carries `Verified:` (`C2-green` or `C2-not-run (<reason>)`). A commit that touches `context/RULES.md` carries `Rules-Audit:` (what changed, contradictions and leaks checked). A commit that touches `context/IDEAS.md` or `doctrine/WORLD-MODEL.md` carries `Direction-Check:` (`<term> -> <contradicted item | none>`). The template is `.gitmessage`.

## E. Sessions and the bookmark

- **E1 — Start.** `bash context/scripts/session.sh start`: git alignment, gates, the pointers of `STATE.md`. Then report to the maintainer (what was read, the state, the `[next]` step, any mismatch between docs and code) before proposing anything.
- **E2 — The bookmark.** `STATE.md` has a fixed shape: `Last commit verified` (the commit before the one that updates the bookmark: the commit-msg hook checks it equals `HEAD`), *Dove siamo* (short, present tense), *Plan* (rows `| [state] | id | what | depends on | first action |`, states `[next] [wip] [open] [deferred] [urgent] [done]`), *Open items* (`| OI-N | what, why it matters | first action |`, each readable by someone who does not know the project). No diary, no list of files touched: that is `git log`. Update it when a step closes, before every push (the bookmark is the last commit before a push: `gates.sh` E4b), and when the context runs out. A closed step or item leaves the file.
- **E3 — Capture.** At a pause or at the end of a task: `bash context/scripts/session.sh capture pause "<what was said> -> <OI-N, IDEA-X-N, ADR-N or none>"`. It records the event in `context/captures/` and verifies that every promotion after `->` exists. It is how an AI without memory of the chat leaves a trace for the next one.
- **E4 — Close.** Only on "chiudi". `bash context/scripts/session.sh close` (C2, gates, capture), then the bookmark, the commit, the push to both remotes, and a short report. After the closing, new work is tracked in `STATE.md`, not done, unless the bookmark is broken, the gate is red, or the maintainer asks.
- **E5 — Ideas.** A new idea goes to `IDEAS.md` as `sketch` (prerequisites, open questions) before it is discussed further. It becomes work only with an ADR or a step in `STATE.md`.

## F. For an AI without a shell

When the maintainer runs the commands for you (copy and paste): one command per message, each wrapped so its output is easy to select, `echo ""; echo -e "\033[1;91m>>> OUTPUT START\033[0m"; <command>; echo -e "\033[1;91m<<< OUTPUT END\033[0m"`; one file change per command, followed in the same block by a check that it happened (`grep -c`, `wc -l`); no code fences inside heredocs; stop at the first unexpected output.
